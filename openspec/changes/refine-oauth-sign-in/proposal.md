## Why

`Backlog.md`'s OAuth sign-in item bundles Google and Apple together, but Apple Sign In requires an active paid Apple Developer Program membership ($99/yr) plus meaningfully more setup friction, and its only justification was parity with Google — a real dollar cost nobody has decided is worth it for a small family app. That same backlog item also flags a design conflict that was never resolved: `identity`'s "Account creation is admin-managed, no self-service" requirement appears to break once any OAuth provider is added, because PocketBase's default OAuth2 flow auto-creates a `users` record for anyone who authenticates successfully.

That conflict turns out to be avoidable rather than unavoidable. Auto-provisioning is a property of PocketBase's *native* OAuth2 flow, not a constraint on the app: a hook that requires a pre-existing `users` record — and creates nothing when there isn't one — preserves the admin-managed requirement exactly as written, with the roster staying in the app that already holds the user records. No external allowlist, no perimeter, and no second source of truth to keep in sync.

## What Changes

- Add **Google** as a native PocketBase OAuth2 provider, configured through PocketBase's own admin/migration config. No custom identity infrastructure is introduced. The Google Cloud OAuth consent screen must be published to **Production**, not left in Testing — Testing mode requires every family member to be individually added as a Google Cloud test user, which is a second approval list to maintain alongside the `users` roster and defeats the "single source of truth" this change is built around. Production is available without Google's verification review because only non-sensitive scopes (`email`, `profile`, `openid`) are requested.
- **Keep the existing email one-time-code (OTP) sign-in, and treat it as the primary method** rather than something to be retired. Not everyone in the family necessarily has a Google account, and OTP's profile fits this app better than any alternative: nothing to enrol, works on a borrowed or brand-new device, and recovery is self-service through an email account the person already owns. Google becomes the fast path for whoever has one.
- **Drop Apple entirely** — the recurring membership cost and extra setup (Services ID, domain/redirect config, signing key) buy nothing that Google and OTP don't already cover.
- **The roster stays in PocketBase's `users` collection, admin-managed.** A `pb_hooks` guard on the OAuth2 sign-in path refuses any federated authentication whose verified email has no pre-existing `users` record, and creates no record in that case. Email OTP needs no such guard: `requestOTP()` already cannot create or send anything for an address with no matching record, which is PocketBase core behavior. This guard is the single security-critical piece of the change and MUST fail closed: an error in the guard has to deny sign-in, never allow it. Concretely, it throws a PocketBase `ApiError` (`ForbiddenError`) rather than a plain `Error`, so the refusal reaches the client as a distinguishable 403 instead of being flattened into a generic "Failed to authenticate." message.
- **The roster email is the sign-in email.** A person's `users` record holds the address they will actually authenticate with, so Google works for whoever's roster address is their Google address. Supporting multiple addresses per person is deliberately out of scope at family scale.
- Additional login methods stay addable later through PocketBase configuration alone — it supports Google, generic OIDC, and OTP simultaneously — so no application code changes to add one.
- **Considered and rejected: routing all sign-in through Cloudflare Zero Trust Access** as a front door, with a Zero Trust email List as the allowlist. Rejected because (a) editing a Gateway List requires the account-wide **Zero Trust Edit** API permission — Cloudflare's [permissions reference](https://developers.cloudflare.com/fundamentals/api/reference/permissions/) confirms no permission is scoped to an individual list or application — so the self-service invite item in `Backlog.md` would need a credential that can also rewrite every other Access application, Gateway policy, and tunnel in the account; (b) Access in front of the frontend hostname would gate the public calendar, contradicting `identity`'s first requirement and `AGENTS.md`'s critical constraints; (c) it requires verifying an RS256 Access JWT against Cloudflare's JWKS inside PocketBase's JSVM, which is more custom auth code than the guard hook above, not less; (d) Access cannot gate `localhost`, leaving local development with no working sign-in path at all; and (e) the Access tenant currently serves one person's self-hosted tools, so this would mean onboarding non-technical family members into personal infrastructure and becoming their support desk. Access's own [External Evaluation](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/external-evaluation/) rule was rejected alongside it, since it would put every sign-in on the critical path of a scale-to-zero Railway service.
- **Considered and rejected: Pocket ID (already running at `id.huskytown.net`) as the family identity provider.** Pocket ID is passkey-only by design — its documentation states it "only supports passkey authentication" — with no email-code, magic-link, or password fallback. For a calendar people open a couple of times a year on whatever device is nearest, that inverts the ergonomics: a passkey enrolment dialog per ecosystem, a QR-code-and-Bluetooth flow to cross from one ecosystem to another, and device-loss recovery that routes through an admin instead of through the person's own email. It also makes sign-in depend on a self-hosted IdP staying up. Adding Pocket ID later as an *additional* PocketBase OIDC provider, for whoever actually wants passkeys, stays open and needs no code change.
- **Considered and deferred: a second OAuth2 provider as a backup to Google.** PocketBase ships ~30 built-in providers, but most (GitHub, Discord, Spotify, etc.) don't match who's actually in this family, and OTP already covers the two backup scenarios that matter — no Google account, and Google being unreachable at sign-in time. The only real coverage gain would be **Microsoft** (Outlook/Hotmail/Live), the plan-B if Google's Production publishing proves impractical; **Facebook** has broader coverage but needs Meta App Review for the `email` permission, which is worse friction than the Google review it would be avoiding, so it's not a viable backup. Not adding one now keeps the sign-in form at two methods and avoids multiplying the per-provider email-mismatch surface described above (each added provider is another address that may not match the `users` roster entry, refused with the same generic error as an unapproved stranger). Revisit only if Google turns out to be a real blocker for someone.

## Capabilities

### New Capabilities
(none — this refines an existing capability's requirements)

### Modified Capabilities
- `identity`: "Passwordless sign-in" broadens from email-code-only to also cover federated sign-in with a supported provider, with the email code remaining available to everyone. "Account creation is admin-managed" keeps its current wording — it needs **no** self-service carve-out — but gains a scenario covering the federated path, where someone who authenticates successfully with a provider but has no pre-existing account is refused and no account is created for them. A new method-agnostic requirement states that sign-in succeeds only for a pre-approved account regardless of authentication method, so the guarantee still holds if another provider is added later.

## Impact

- `Backlog.md`'s "Identity via Cloudflare Access" entry is replaced by this decision, and its self-service-invites item loses its hardest dependency: inviting someone becomes a `users` record create, needing no Cloudflare API credential at all.
- Future implementation (not part of this change): Google OAuth2 provider config via `pocketbase/pb_migrations/`; a new guard hook in `pocketbase/pb_hooks/` (currently empty) that throws a `ForbiddenError`, with a documented manual verification of the fail-closed path (no backend test framework exists in this repo); `AuthContext.tsx` gaining an OAuth2 sign-in method alongside `requestOtp`/`confirmOtp`; `SignInForm.tsx` gaining a Google button beside the existing email-code form.
- External setup: an OAuth client ID/secret from Google Cloud Console, with the consent screen published to Production (see above) rather than left in Testing.
- Unchanged by design: the public calendar stays fully unauthenticated with no gate anywhere near it; the Resend/SMTP relay stays wired, since OTP stays; local development keeps a working sign-in path, with `mise run pb:serve` continuing to print codes to the console.
- No Cloudflare Access applications, Zero Trust Lists, or Cloudflare API tokens are introduced.
- No code changes in this change — planning and requirement refinement only.
